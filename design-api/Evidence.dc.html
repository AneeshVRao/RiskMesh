Three shape decisionsand what each prevents

DecisionReason
signals is an array, not an object The ledger and the bar are both ordered by contribution. An object makes order a client concern and invites two panels disagreeing. The server owns the order.
ip_sharing is present with weighted:false Never filtered out. The zero-weighted signal is a finding (RISK-001), not an absence — the UI greys it, and dropping it server-side would hide the most interesting thing on the panel.
separating_fields is server-computed The comparison panel highlights exactly the fields that differ materially. Deciding that client-side would embed analysis in CSS.

peer_rule · frozena documented heuristic, not an implicit default

Rule: nearest-scoring opposite-label component within the same split, preferring hard negatives. This is a heuristic choice, not a derived optimum — recorded here for the same reason every other choice in this project is recorded, so a reader can disagree with it explicitly rather than discover it by reading code.

#StepWhy
1Same split as the subject Never compare across the split boundary.
2Opposite is_positive; exclude self The panel's whole point is ring versus not-ring.
3Prefer has_family == 1 if any exist The panel is “ring vs household”. A generic background negative would not tell the story; the hard negative is the instructive foil. Only ever binds when the peer is a negative.
4Minimise |score_subject − score_peer|, rounded to 9dp Nearest in score is the hardest case to tell apart. Rounding avoids float-representation ties.
5Tiebreak A — higher score wins Two peers equidistant above and below: prefer the harder one.
6Tiebreak B — lexicographically smallest component_id Total order. Guarantees one answer even on exact score ties, and makes the result independent of row order in the CSV.
Verified against the frozen data
Run over all 12 flagged test components: yields c_a00533 → c_a00727 as the mockups show, zero distance ties occur, and the selection is identical across 50 shuffles of the input order. Steps 5 and 6 never fire on today's data — they are specified anyway, because a different seed could produce a tie and that is exactly the kind of thing that should not be discovered at implementation time.

Known consequence: all six escalated rings resolve to the same peer, c_a00727 — it is the highest-scoring family negative in the split, so it is genuinely the nearest foil for each of them. The comparison panel therefore shows the same household on six different ring pages. That is correct under the rule and arguably desirable (one stable reference point), but it is a consequence worth knowing rather than a surprise.

Because every input is a frozen artifact and the rule is a total order, the peer is reproducible run-to-run at the same seed without needing to be precomputed. If that ever stops holding, the fallback is to freeze one designated foil per flagged component into graph_edges.json's sibling record.
