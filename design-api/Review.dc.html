What it doesand the three things it does not

It appends one line to an audit log and returns it. That is the whole endpoint. The UI already says “written to audit trail · no auto-block” under the action bar, and the backend must make that literally true rather than aspirational.

DoesDoes not
Append a timestamped record with an evidence snapshot Not change the component's score, band, or action
Record whether the analyst agreed with the system Not block, decline, or hold any payment
Return the written record for optimistic UI append Not write to any file under out/ that the pipeline owns

An escalation opens a case. Nothing downstream of this service consumes the log; it exists so a decision made today stays explicable after the scorer changes.

Request & recordout/audit_log.jsonl, one line per action

// POST /rings/c_a00533/review
{ "action": "escalate",        // allow | watch | review | escalate
  "analyst": "demo",
  "note": null }

// appended verbatim to out/audit_log.jsonl, and returned 201
{
  "ts": "2026-08-26T14:03:48Z",         // UTC, ISO-8601
  "component_id": "c_a00533",
  "analyst_action": "escalate",
  "analyst": "demo",
  "note": null,

  // --- what the system said at decision time -----------------
  "score": 0.5246,
  "band": { "t_lo": 0.23, "t_hi": 0.33 },
  "system_action": "escalate",
  "agreed_with_system": true,        // the one derived field
  "config_fingerprint": "7c1e4fb2b329796c",

  // --- evidence as it stood, not a pointer to it -------------
  "evidence_sha256": "a3f1c8...",
  "evidence_snapshot": {
    "signals": [ /* the decomposition array, verbatim */ ],
    "summary": { "size": 9, "n_txns": 101, "exposure": 101761.83 }
  }
}

The snapshot is embedded, not referenced. A foreign key into components.csv would silently change meaning the next time the pipeline re-freezes; the point of an audit trail is that it still says what the analyst actually saw. The evidence_sha256 lets you detect that the live evidence has since moved without having to diff the whole block.

Storagerecommendation: append-only JSONL

ConsiderationJSONLSQLite
Access pattern — append, then tail-N per component Native. Append is one write(). Works, but the index earns nothing at this row count.
Nested evidence_snapshot Natural. It is already JSON. A TEXT column holding JSON — SQLite as a filesystem.
Fits the project's existing discipline Yes. Everything else is JSON/CSV on disk: greppable, diffable, committable. Introduces the one opaque binary in an otherwise inspectable tree.
Dependencies & lifecycle stdlib json. No connection, no migration, no schema DDL. stdlib too, but adds connection handling and a schema to version.
Concurrent writers One process, single append. Fine. Wins here — but there is only ever one writer.

Recommendation: out/audit_log.jsonl, append-only. A demo writes tens of records, one process, appends only, and reads them back newest-first for one component. Every advantage SQLite has over a flat file — indexes, transactions, concurrent writers, query planning — is an advantage over a problem this service does not have. The flat file is also the only option a judge can cat.

When this flips
Switch to SQLite the moment any of these becomes true: more than one writer process, a need to query across components (“every escalation last week”), or mutable records (edit or retract a decision). None are in Tier 1 scope. Writing the reader in audit.py behind two functions — append(record) and tail(component_id, n) — keeps that swap to a single file.

Durabilityhonest about what append-only guarantees

Open in "a" mode, write one json.dumps() line with no embedded newlines, flush. A torn write can only ever corrupt the final line, and the reader skips unparsable lines rather than failing the request — so a crash mid-append costs at most the record being written, never the history. That is the correct trade at demo scale, and it is a deliberate ceiling rather than an oversight.
