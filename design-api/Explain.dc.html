Cut this firstthe recommendation, up front

Drop before anything else
Per the PRD's Tier 1 fallback rule, this is the first thing to cut if time is short — and it should be. The deterministic fallback already exists and already ships. score_component() writes a detail string for every signal (“9 accounts share device d_ring02”, “median account age 10 days”), and the mockups already read as plain English from those strings alone. An LLM layer would make the narration smoother; it would not make it more informative, and it adds the only component in the system that can be wrong in a new way.

Design the contract now so the door stays open. Build it only if the four tabs are wired, the audit trail works, and there is genuine slack.

Contractinput is an id, never numbers

// POST /explain
{ "component_id": "c_a00533",      // an ID. Nothing else.
  "audience": "analyst" }         // analyst | executive

// 200
{
  "component_id": "c_a00533",
  "text": "Nine accounts transacted from a single device. Six of them
            reached one merchant inside thirty minutes, and the accounts
            were a median of ten days old. Each kept its own IP, which is
            what separates this from a household sharing a router.",
  "grounded_in": ["device_sharing", "temporal_burst", "account_newness",
                   "ip_sharing"],
  "numeric_tokens": ["9", "6", "30", "10"],   // each verified present
  "config_fingerprint": "7c1e4fb2b329796c",
  "fallback_used": false
}

The request carries no numbers. The caller names a component; the server reads the frozen evidence itself and builds the prompt from it. A client cannot supply a score, a signal value, or a claim — so it cannot induce the model to narrate something the detector never said.

Grounding contractfour rules, enforced not requested

RuleEnforcement
1. Cannot invent values. Every numeric token in the output must appear in the evidence block. Post-generation validation. Extract numerics from the text; any token absent from the evidence → reject the generation.
2. Cannot override the detector. It may not state or imply an action different from action. The action is never in the model's output path — the UI renders it from the evidence response. The narration sits beside it, not above it.
3. Cannot introduce a signal. Only signals present in the decomposition may be named. Reject any generation naming a term outside grounded_in.
4. Always degrades, never fails. On rejection or timeout, return the deterministic detail-string composition with fallback_used: true. The endpoint has no error path the UI must handle.

Rule 1 is the one that matters and the one that is cheap: a regex for numeric tokens plus a set membership test against the evidence block. It cannot catch a fluent mischaracterisation, but it does catch the failure that would actually embarrass this project — a confident number that is not in the data.

Honest limitswhat the validator does not buy

Numeric validation is not a correctness proof. A generation can pass every rule above and still misattribute causality — “the accounts were created to commit this fraud” contains no numbers and names no new signal, but claims intent the detector never established. There is no cheap enforcement for that.

Which is the real argument for cutting it. The deterministic composition cannot make that class of error at all, because it only ever concatenates strings the scorer wrote. An explanation layer that can be subtly wrong is worse than a blunt one that cannot be, on a project whose entire credibility rests on the numbers being trustworthy.
